Photo Meta Organizer · UI exploration

Three directions for the frontend

Each prototype is a working, clickable mock-up on the same 18-photo sample library. Filters, rating, picking, selection and keyboard shortcuts all work. Open one, then press Design notes to see what changed in each component compared with today's UI, and why.

Prototype A

Darkroom

Photo-first and neutral. The interface steps back so the pictures carry the colour. Built for culling and rating.

  • Icon nav rail replaces the crowded header
  • Justified rows, no cropping
  • Histogram computed from real pixels
  • Amber accent only for picks and selection

Prototype B

Atelier

Editorial and warm. The library reads like a photo book, with trips as chapters and metadata as captions.

  • Chip filter bar replaces the sidebar
  • A plain-English sentence restates the filter
  • Chapters by trip with a hero mosaic
  • Detail sheet styled like a museum label
Open prototype →
Prototype C

Console

Dense and keyboard-first: the library as data, with an IDE-style workspace for metadata power users.

  • Token query bar: iso:>=1600 tag:night
  • Facets double as distribution charts
  • Sortable table with range selection
  • Summary / EXIF / JSON inspector and a status bar

How they compare

A · DarkroomB · AtelierC · Console
Best forCulling, rating and picking large shootsBrowsing and reliving trips; sharingSearching, auditing and comparing metadata
MoodQuiet, neutral dark (Lightroom-like)Warm paper, serif type (photo book)Graphite and mint, monospace numbers (IDE)
Information densityMedium: photos dominateLow: generous whitespaceHigh: about 20 rows of metadata per screen
FilteringLibrary panel with count bars and chipsChip bar, popovers and a describing sentenceTyped query tokens and clickable facet bars
InspectorSide panel: preview, histogram, exposure stripFull detail sheet with a minimapTabbed: Summary / EXIF / raw JSON
Change to the React codeMedium: new NavRail; restyle gallery, card and inspectorMedium to high: new information architecture (FilterBar, chapters, sheet)Medium: QueryBar, PhotoTable, StatusBar; fits current components
Backend changesNone (uses existing dimensions)None (groups by captured_at and GPS on the client)None for make, tag, rating, date and text tokens; ISO/aperture/focal ranges would need new API fields
Suggestion: the three can be combined. A sensible path is A's neutral palette, nav rail and justified grid as the base, then C's query bar and table as a second layout in the studio view, and B's chapter grouping for the Timeline view. Each step ships on its own and keeps the existing stores, hooks and API.

Each prototype is a static HTML file with no build step. The sample photos are procedural SVGs from shared/sample-library.js; in the real app they come from /api/photos/{hash}/thumbnail. Fonts load from Google Fonts; everything else works offline.
