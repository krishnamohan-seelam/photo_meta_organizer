# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Photo Meta Organizer indexes large photo libraries: it extracts EXIF, keys every photo by SHA-256 of its contents (dedup), and stores results in SQLite (`photos.db`), behind the same repository port. Three front doors share one backend: a CLI (`main.py`, the commands in `cli/`, Typer), a FastAPI REST API, and a React 19 SPA that can also be wrapped in an Electron desktop app. README.md lists phases 0–4 as complete and phases 5–6 (AI tagging, S3/MongoDB) as planned. Note the numbering conflict: `design_docs/PHASE_5_COMPLETION.md` labels the finished Electron desktop app as "Phase 5", while the README treats the desktop app as part of the current state. The S3 and MongoDB backends and AI tagging do not exist yet.

## Repository layout (non-obvious bits)

The repo root is the uv project root: `pyproject.toml` (runtime deps, `dev` and `build` dependency groups, optional `s3` extra, ruff/black config), `uv.lock` and `.python-version` (3.11) live there, and `uv sync` manages `.venv` at the root. The package `photo_meta_organizer/` is installed editable, so it imports from any directory. Inside the package, `pytest.ini` is the only pytest config and `setup.cfg` holds only the mypy config. The version's single source is `photo_meta_organizer/__init__.py` (`__version__`; the API and `--version` read it). The root also holds `frontend/` (Vite SPA), `desktop/` (Electron), `scripts/` and the npm workspace `package.json`.

Runtime files live outside the repo, in the OS per-user folders split by kind (`application/settings.user_dirs`, via `platformdirs`; `main paths` prints them): data (`photos.db` plus `-wal`/`-shm`, `models/` with the AI model and its label-vector cache) in `%LOCALAPPDATA%\PhotoMetaOrganizer` / `~/Library/Application Support/...` / `~/.local/share/...`; thumbnails in the matching cache folder (`...\Cache`, `~/Library/Caches/...`, `~/.cache/...`); logs in the log folder. The CLI, the API and the desktop app therefore share one library from any working directory. `PMO_DATA_DIR=<dir>` puts everything under one folder (a scratch library). The CLI writes a rotating `photo_meta_organizer.log` only with `--log` (OS log folder), `--log-dir` or `PMO_LOG_DIR`; the desktop backend always writes `backend.log` (logging is configured at startup by `infrastructure/logging_setup.py`, never at import; log lines go to stderr). A CLI command that falls back to the default library while a `photos.db` sits in the CWD prints a note saying where the library now lives. The repo root may still hold the pre-change `photos.db*` and `.cache/` (git-ignored); don't commit or casually rewrite these. A pre-migration `metadata.json` (the old TinyDB store, ~16 MB) may still sit alongside it as a legacy artifact — see ADR-001 below; `*.bak*` files are stray backups.

## Architecture

Clean Architecture with Protocol-based ports. Dependencies point inward: `api`/`cli` → `application` → `domain`; `infrastructure` implements the `application/interfaces` Protocols. (The CLI still imports a few infrastructure pieces directly, as `main.py` did: `logging_setup`, `metrics.ProgressReporter`, `ModelStore`/`ModelUnavailableError`.)

- **domain/** has no I/O and its models are frozen dataclasses. `models.py` holds `ImageMetadata` (the aggregate, keyed by `file_hash`), the three-tier `ImageExifData` (universal → common → camera-specific plus `raw_tags`), and the sync types `FileInfo`, `FileState`, `SyncResult`. `services.py` holds `CameraClassifier` and `MetadataStateAnalyzer`. Small rule modules: `curation.py` (rating 1-5, tag and label rules, shared by the API schema and the repository), `datetimes.py` (`to_naive`), `formats.py` (`IMAGE_EXTENSIONS`, `is_image_filename`).
- **application/interfaces/** defines three Protocols: `ImageRetriever` (discover files and open streams), `ImageMetadataExtractor` (stateless: `extract(file_handle, stream)`) and `ImageMetadataRepository`. Use cases live in `use_cases/` (`ScanLibrary`, `SearchPhotos`, `PruneNonImages`, the analysis ones). There is one ingest pipeline, the scan (ADR-003 R4).
- **infrastructure/** is organized into subpackages: `retriever/` (`LocalDiskRetriever` wrapped by `ExtensionFilteredRetriever`, `S3ImageRetriever` — imports `boto3` via the optional `s3` extra, not wired into any CLI or API path), `extractors/` (`DiskMetaDataExtractor`), `repositories/` (`SqliteRepository`/`SqliteCollectionRepository` — the live backend, ADR-001; no other backend), `importers/` (`legacy_json_importer.import_legacy_json`, one-time TinyDB → SQLite migration, reading through the read-only `legacy_json_reader.LegacyJsonReader`; tests build legacy files with `tests/legacy_json.LegacyJsonWriter`; the `tinydb` dependency goes one release later), plus `ThumbnailService` and `metrics.ProgressReporter`.

**Composition root:** `application/settings.Settings` (frozen; flag > `PMO_*` env > default) is the one configuration object for the CLI (`--db`), `api.app.create_app(settings=...)` and the desktop backend (`api/desktop.py`); with nothing set, its paths default to the OS per-user folders (`user_dirs()`, looked up at call time so tests can replace it; `tests/conftest.py` has an autouse `user_dirs` fixture that points them at a temp dir and clears the `PMO_*` path variables, so no test touches the real AppData). `build_repository` creates the database's folder. `application/composition.py` builds retrievers and repositories for all of them: `build_repository(db_path)` always returns a `SqliteRepository`, transparently importing a legacy `.json` file into a sibling `.db` file the first time it's pointed at one (the `.json` is left untouched). `create_app` stores a `Services` container on `app.state`; routes get the repository, collections, job manager and thumbnail service through `api/dependencies.py`, typed as the application Protocols. There is no `dependency_overrides` wiring in production. `build_scan(folder, repository, progress_reporter=None)` builds the retriever, extractor and scan; the CLI's `index`/`sync` and `POST /api/index`/`/api/sync` only call it (tests that need a failing extractor patch `infrastructure.extractors.disk_metadata_extractor.DiskMetaDataExtractor`).

### Data flows to understand before changing them

- **The scan** (`application/use_cases/scan_library.ScanLibrary`, ADR-003 R4, ticket 05) is the only ingest path: `index` is a scan without `remove_missing` (unchanged files are skipped, so a second `index` reads nothing), `sync` is the user-facing name with every option. `execute(ScanOptions(remove_missing, rehash, reextract, dry_run, workers=4, index_new, reprocess_modified), scope_root=, progress=(done, total), should_cancel=)` returns a `SyncResult`. Classification and bookkeeping (missing flags, fingerprints, removals) run on the calling thread; NEW and MODIFIED files are hashed and extracted on a `ThreadPoolExecutor` (a window of `2 * workers` in flight, so a cancel stops quickly), and results go through a bounded `queue.Queue(100)` to a **single writer thread** that saves them with `save_many` in batches of up to 100 (falling back to one `save` per record to report the one at fault). `SqliteRepository` is thread-safe anyway, so the writer thread is a serialization choice. The API's index job keeps its `total`/`indexed`/`failed` counts (`job_work.scan_work(..., kind="index")`).
- **Incremental sync** (what a scan does with what it finds): the disk scan builds `FileInfo` per path, `repository.list_files()` gives one `StoredFile` per recorded File, then `MetadataStateAnalyzer.analyze_changes` (pure) classifies each path as NEW / MODIFIED / UNCHANGED / DELETED, and the scan applies the changes according to its options. A File the scan did not find is a **Missing file** (ticket 04): by default it is kept and flagged (`files.missing_since`, set once via `repository.set_missing`, cleared when the path reappears or is re-saved; `SyncResult.missing_files`/`found_again`), so moving a folder out and back loses nothing. Removing them is opt-in (`--cleanup-deleted`, alias `--remove-missing`; `ScanOptions.remove_missing`): it forgets the File (`delete_by_path`), and the Asset only once no File holds it. A root that cannot be read raises `RootUnavailableError` before anything is classified and again after listing (the CLI prints it and exits 1), and Files under folders or files the listing could not read (`ImageRetriever.skipped_paths()`; `LocalDiskRetriever` walks with `os.walk(onerror=...)`) are left out of the comparison, so they are never flagged or removed. `--dry-run` reports counts and writes nothing. Exit code is 2 if any per-file errors occurred.
  - **Fingerprint is (size, mtime).** `ImageFileInfo.modified_time` is stored on every record (naive local time; the scan stamps it from the disk listing, `DiskMetaDataExtractor` also sets it). If size or mtime differs the file is hashed: same hash is UNCHANGED, a different hash is MODIFIED. Legacy records with no stored mtime are trusted on size alone and backfilled (`FileState.refresh_fingerprint` → `repository.refresh_fingerprints`, keyed by path, one batched write, reported as `SyncResult.fingerprints_refreshed`). An edit that keeps both size and mtime is only caught by `sync --rehash`.
  - **An edit moves a pointer** (ADR-003 R3). Content is the key, so an edit changes the hash. The scan just calls `repository.save(new)` (on the File it matched, `FileState.recorded_path`): the path's `files` row now points at the new Asset, and `SqliteRepository._carry_over` merges the old Asset's curation in (`domain.curation.merge_curation`: first rating, any flag, union of labels) and its collection membership. It is *moved* (the old Asset is deleted, with its embeddings and tags) when no other File holds the old content, *copied* when one does. `replace()` and the `dedupe` command are gone.
- **SqliteRepository** (ADR-001, ADR-003 R3, `infrastructure/repositories/sqlite_repository.py`): the live backend. Schema version 7 (migrations `0002 split_assets`, `0003 missing_files`, `0004 jobs`, `0005 roots`, `0006 hidden_files`, `0007 removal`) stores each Asset once in `assets` (extracted metadata plus the content's `size_bytes`), each path in `files` (`path UNIQUE`, the (size, mtime) fingerprint, `first_seen`/`last_seen`), and curation in `curation` + `asset_labels`; `photo_embeddings`, `photo_ai_tags` and `collection_photos` reference `assets(file_hash)` with `ON DELETE CASCADE`. Two views: `asset_view` (assets + curation) is what search filters, sorts and counts (`search_source` picks plain `assets` when no rating/flag filter needs the join), and `photo_view` adds each Asset's **primary file** (a present File first, then latest `last_seen`, lowest `id` on a tie; migration 0003) for the rows actually returned. So `query()` pages hashes first and reads full rows only for the page. Path and name search match any File of an Asset. Every Asset has a curation row and at least one File (an Asset is deleted when its last File goes). It holds one shared `sqlite3.Connection` (`check_same_thread=False`, WAL journal mode) guarded by an `RLock`. Collections live in their own tables, via `SqliteCollectionRepository` sharing the same connection/lock. The old TinyDB repository is gone (ticket 19): an old `.json` file is only read, once, by `infrastructure/importers/legacy_json_reader.py` for the migration into a `.db` file. Curation goes through typed commands only (`apply`/`apply_batch`); the dict-based `update_metadata`/`batch_update` no longer exist. `python -m photo_meta_organizer.scripts.benchmark_search --count 100000` times search through the port (results in ADR-003).
- **Datetimes are naive local time** (ADR D3): EXIF has no timezone, so `captured_at` is a naive wall-clock value. Anything with tzinfo (API bounds ending in `Z`, old records) is reduced with `to_naive`, which drops tzinfo without shifting the clock. `SearchPhotosQuery` normalises its own bounds.
- **Curation input is validated in three places on purpose:** the Pydantic schema (422), `SqliteRepository` (raises `ValueError`, which the router maps to 422) and `_to_response` (tolerates a bad stored rating). Batch `action` is a `Literal`, `delete` is reported as `deleted_count`.
- **Duplicates** (ADR-003 R11, ticket 03): an Asset with more than one *copy* (a File on disk, `hidden_at` unset). `files_of`, `duplicate_groups`, `set_file_hidden` on the repository; `paths` on every photo response (build responses with `photos_router.to_responses`, one query for the page, not `_to_response` alone); `GET /api/duplicates`, `POST /api/files/hide` (under `/api/files`, which announces `library_changed`); filter `duplicates`/token `dupes:`. A scan that finds the same content at a path keeps its `hidden_at`; a path whose content changed gets it cleared. The duplicates list also keeps groups resolved by hiding (`total_listed`), so a hidden copy can always be shown again. Nothing deletes files on disk.
- **Identity:** `file_hash` (SHA-256) is the Asset's key and `save()` is an upsert on it plus an upsert of the File on its path, so identical content at two paths is one photo with two Files (a Duplicate, see `GLOSSARY.md`). `ImageMetadata.file_info` is the primary file; `list_files()` lists them all. Sync matches on resolved path, not hash.
- **User curation fields** (`rating`, `flagged`, `labels`) are stored in `curation`/`asset_labels`, and `save()` of an existing record updates only the extracted columns and keeps the stored curation (ADR-003 R2); `save(..., overwrite_curation=True)` is for callers that merged curation themselves. A new record is stored with the curation it arrives with.

### CLI

`main.py` is only the entry point (`main()` → `cli.run(argv)`). `cli/app.py` holds the Typer app: global options (`--version`, `--log-level`, `--log`, `--log-dir`) in its callback, then one module per command (`cli/index.py`, `sync.py`, `search.py`, `stats.py`, `prune.py`, `analyze.py`, `paths.py`). Each command calls `common.start(ctx, db, model_dir)` first (Settings flag > env > default, the "library left behind" note, logging) and ends with `common.finish(code)`. `run()` returns the command's exit code and turns usage errors into `SystemExit(2)` like argparse did; Typer 0.27 vendors click, so catch `typer.TyperException`, not `click` exceptions. Options use `Annotated[..., typer.Option(...)]` (ruff's B008 stays quiet) and `Literal` for choices. Commands are registered with `cls=common.Command` (the root with `cls=common.Group`): it accepts any unambiguous prefix of a long option as argparse did (`--dry`) and hides Typer's `[default: X]` because each help text says its default; the app sets `rich_markup_mode=None` so help is plain ASCII. Docstrings are the user's `--help`: keep ADR notes and RST out of them. Ctrl-C exits 130 (Typer).

### API and frontend

`api/routes/photos_router.py` defines the photo, collection, search/facets, index, sync and job routers; **jobs are stored** (ADR-003 R5a, ticket 07): `JobManager(store=composition.build_job_store(repository))` writes every job through to the `jobs` table (migration 0004; `SqliteJobStore` on the shared connection; progress at most once a second) and loads the last 50 at startup. A job still `queued`/`running` at startup, or stopped by `shutdown()` without the user cancelling, becomes `interrupted`; it is never resumed on its own: `POST /api/jobs/{id}/resume` (same id, its stored `params`; an analysis resumes with `reanalyze` off) or `/dismiss` (ends `cancelled`), 409 if it is not interrupted or its folder is busy. Every job's work is built by `api/job_factory.work_for(kind, folder, params, services)`, used both by the routes that start jobs and by resume, so a new job kind must be added there. The `JobStatusPill` shows 'Interrupted: ...' with Resume / Dismiss. **Events** (ADR-003 R5b, ticket 08): `GET /api/events` (`api/routes/events_router.py`) streams server-sent events from `application/events.EventBus` (`job_progress`, `job_finished`, `library_changed`, `resync`; increasing ids, ring buffer of 200, `Last-Event-ID` replay, `resync` for an older gap or an id from another run (wire ids are `<run>.<n>`, `EventBus.run_id` changes per server start); `Services.events`, closed by the lifespan so streams end). `JobManager(on_event=job_event_handler(bus))` publishes jobs (a job ending also publishes `library_changed`), and an HTTP middleware in `create_app` publishes `library_changed` after a successful edit under `/api/photos`, `/api/collections`, `/api/ai-tags`; a new route that edits the library must be under one of those prefixes (`changes_library`). **Roots** (ADR-003 R11, ticket 09): the library remembers the folders it scans (`roots` table via `RootStore`, `Services.roots`; `api/routes/roots_router.py`: `/api/roots`, `/api/roots/suggestions`, `/suggestions/dismiss`). The lifespan calls `application.roots.scan_roots(roots, jobs, make_work)` (work built by `job_factory.scan_work_factory`) when `Settings.scan_on_start` (`PMO_SCAN_ON_START=0` turns it off; tests with roots use it): a non-removing `sync` job per readable root, an offline root skipped quietly (`online: false`); the CLI never does this. An existing library with no roots is offered `suggest_roots(observed_folders())` once (`RootSuggestionsDialog`); "Not now" is stored in `library_state` and nothing is watched silently. **Removal** (ticket 12): removing is soft and undoable. `remove_assets` sets `assets.removed_at` (reads go through `live_assets`/`asset_view`/`photo_view`; a new query over assets must too), `restore_assets` clears it, and `TrashPurger` (30 s `UNDO_SECONDS`, and everything at start) calls `purge_removed`, which records each File's path/size/mtime in `ignored_files` (missing Files too) and deletes the Asset. A removed Asset saved at a path it does not hold (a copy found inside the undo window) is purged first, so the copy is a new photo and the removed paths stay ignored. `facets()` labels and `count_embeddings` count live Assets only; `list_files` deliberately includes removed ones, so a scan in the undo window sees them as unchanged. `POST /api/removed/restore` acts only on paths in the ignored list. The scan skips a NEW path whose size and mtime still match an ignored entry (`FileState` `IGNORED`, count `ignored`); a File saved at a path drops its entry. `DELETE /api/photos/{hash}` and batch `delete` are these soft removals; `POST /api/photos/restore`, `GET /api/removed`, `POST /api/removed/restore`. **Keep analysed** (ticket 11): `application/keep_analysed.KeepAnalysed` (off by default; setting in `library_state` through the `StateStore` port; `GET/PUT /api/analysis/keep`) starts an `analyze` job on its own only when the model is installed, at most `PMO_KEEP_ANALYSED_MAX` (2,000) photos wait (else state `needs_approval` and the pill asks), no job runs or is paused, the user has been still 30 s (`ActivityTracker`, touched by non-GET requests) and, in the desktop backend (`ac_power_only`), the computer is plugged in. `JobManager.pause`/`POST /api/jobs/{id}/pause` leave a job `interrupted` ('Paused. ...') for Resume. **Watching** (ticket 10): `application/root_watcher.RootWatcher` (built in `create_app` when `Settings.watch_folders`; `Services.root_watcher` is None otherwise; `PMO_WATCH_FOLDERS=0` or the tests' conftest turn it off) watches readable roots through the `FolderWatcher` port (`infrastructure/watching`, `watchfiles`), waits 5 s of quiet, then scans only the changed folders (whole root above 1,000), re-tests the roots every 30 s and on `POST /api/roots/recheck` (the SPA sends it on window focus). Tests drive `tick()` with a fake clock and `tests/fakes.FakeFolderWatcher`. `FirstRunState` (empty library: choose folder → live scan → optional AI setup) and `FoldersDialog` ("Watched folders…" in the palette) are the UI. The SPA opens one `EventSource` in `hooks/useEventStream.ts` (upserts jobs, invalidates photos/facets, polls jobs via `useJobs` only while the stream is down); `api/routes/export_router.py` streams ZIP and JSON exports. `_to_response` converts domain objects to the Pydantic schemas in `api/schemas.py`, so adding a domain field means touching the model, `sqlite_repository._asset_row`/`_from_row` (and `_upsert` for File columns) (and the schema, as a new numbered migration in `infrastructure/repositories/migrations.py`; `PRAGMA user_version` tracks it, a newer database is refused), `schemas.py` and `_to_response`, then regenerating the frontend types (`frontend/src/api/schema.ts` is generated; `types/metadata.ts` only aliases it). Response models inherit `ResponseModel`, so fields with defaults are required in the generated types. `/health` returns `{"status": "ok", "photo_count": ...}`, which the Electron shell uses to detect an already-running backend. Thumbnails (and `/preview`, a 2048 px WebP the lightbox uses) are WebP, cached on disk under `Settings.thumbnail_dir` (the OS cache folder) and addressed by file hash; the cache is written atomically, renders are single-flight per key, and it is bounded by `PMO_THUMBNAIL_CACHE_MB` with LRU eviction. **AI analysis storage (Phase 5, ADR-002; storage, model adapter, the `analyze` CLI/job, the HTTP surface and the UI exist):** `AnalysisRepository` (`application/interfaces/analysis_repository.py`, built by `composition.build_analysis_repository`, implemented by `SqliteAnalysisRepository` on the same connection and lock) keeps unit-length float32 embeddings per `(file_hash, model_id)` and *suggested* tags (`suggested`/`accepted`/`rejected`) in `photo_embeddings`/`photo_ai_tags`, both `ON DELETE CASCADE` from `assets`, so a modified file (its old Asset deleted when no File holds it) drops its stale results while re-saving unchanged content keeps them. `nearest()` is brute-force numpy cosine over a per-model matrix cached in memory (rebuilt when this repository writes, when another connection writes (`PRAGMA data_version`) or when the row count changes; measured at 100k photos: about 1.9 s cold, 40 ms warm unfiltered, 120 ms with a 25% filter, filters applied as a hash set from SQL). `SearchQuery.ai_tag` filters to photos with an *open* suggestion of that label (`SearchRequest.ai_tag`, the Library panel's "Suggested by AI" and a `✨ label` chip). `AnalyzePhotosUseCase.retag()` (CLI `analyze --retag`, API `AnalyzeRequest.retag`) recomputes open suggestions from stored vectors without opening photos. AI tags never touch the user's `labels`; accepting goes through the curation path. `ImageEmbedder` is the model port (`embed_image(stream, filename)`, `embed_text`), implemented by `infrastructure/analysis/clip_onnx_embedder.ClipOnnxEmbedder` (CLIP ViT-B/32, ONNX Runtime, fp16 weights, lazy-loaded; `preprocess_image` is pure). The model files are described, pinned and checksummed by `model_manifest.CLIP_VIT_B32_FP16` and downloaded only with consent by `ModelStore` (verify then atomic rename; `PMO_MODEL_DIR`). `ZeroShotTagger` scores a stored vector against `application/tag_vocabulary.VOCABULARY` (541 labels, prompt `a photo of a {}`, softmax of 100 x cosine, defaults limit 8 / threshold 0.05, label vectors cached on disk). `AnalyzePhotosUseCase` embeds `pending_photos` in batches on a small thread pool and stores from one thread; `job_work.analyze_work` runs it as a job. Composition: `build_model_store`, `build_embedder`, `build_tagger`. Decisions and measurements (fp16 over int8) are in ADR-002. **HTTP surface** (`api/routes/analysis_router.py`): `Services` also carries `analysis`, `model_store`, `embedder`, `tagger`, and `create_app(..., model_store=, embedder=)` are the test seams (the API tests run on `FakeImageEmbedder` plus a model 'served' from a temp file via `file://`; monkeypatch `infrastructure.analysis.runtime.ai_runtime_installed` for the missing-extra paths; both routers look it up through that module). The model download and the analysis are jobs (`kind` `model-download`, `analyze`) that share one job 'folder' (the models directory) so they exclude each other; download progress counts bytes and needs the body `{"accept": true}`. Status codes: 503 without the `ai` extra, 409 without the model / nothing analysed / a job already running, 404 unknown photo or label. `ResolveAiTagsUseCase` (accept = `AddTag` through the metadata repository then mark; reject and reset only mark, no action removes a label) and **Review queue** (ticket 18): `analysis.review_labels/review_items/count_open`, `GET /api/ai-tags/review[/items|/count]` and `POST /api/ai-tags/accept-above` (`ResolveAiTagsUseCase.accept_above`); UI `components/review/ReviewSuggestionsDialog.tsx` (A/R/J/K, bulk accept shows the count first). `SemanticSearchUseCase` (text or `like_hash`, filters via `SearchQuery`) hold the logic. `tests/fakes.py` has a deterministic `FakeImageEmbedder` for tests. **AI UI** (`frontend/src/components/ai/`, `hooks/useAnalysis.ts`, `utils/analysis.ts`): `AiSetupDialog` (opened by the top-bar sparkle button or the palette; store `aiDialogOpen`) shows size, source and licence from `GET /api/analysis/status`, and sends `{accept: true}` only when Download is pressed; `analysisStep(status)` picks the dialog's state. The download and the analysis are ordinary jobs, so `JobStatusPill`/`useJobCompletionNotices` show them (the download counts bytes). A search by meaning is store state `semantic` (text or like-this-photo): `QueryBar` offers “Search by meaning” (or the setup dialog when not ready), `LibraryView` swaps its list for `SemanticResults` (top 60, best first, under the current filters, no paging, no lightbox), and `AiTagsSection` in the inspector lists suggestions (accept/dismiss) and a Similar strip that ignores the Library filters. `SelectionDock` has “Accept suggestions” when something is analysed. `SemanticResults` shows the top `semanticLimit` matches (store; 60, "Show more" adds 60 up to the API's 200), uses `useLibraryHotkeys` and opens `LightboxModal`, which pages through the semantic photos while `semantic` is set. Semantic features are off in `?demo=1`. `build_backend.py` adds onnxruntime/tokenizers to the PyInstaller bundle when installed (`npm run backend:package` passes `--extra ai`); the model is never bundled. **Map view:** `POST /api/geo/clusters` (search filters + `bbox` viewport + `zoom`) returns grid clusters from `repository.geo_clusters` (SQL `GROUP BY` on a cell sized by `application/geo.cell_degrees_for_zoom`; keep `frontend/src/utils/geo.ts` in step), each labelled by the `PlaceNamer` port (`infrastructure/geo/offline_place_namer.py`, a bundled GeoNames `cities.tsv.gz` built by `scripts/build_cities.py`, listed in `scripts/build_backend.py` as PyInstaller data; no network). `SearchRequest.within` is the separate map-area *filter* behind "Show these in Library" (store `filterArea`, a chip, not a query-bar token); the Map view's own requests drop it. `GET /api/config` exposes opt-in `PMO_MAP_TILES_URL` (validated `http(s)` template); with none, `LeafletMap.tsx` draws the bundled `world-atlas` outline, so no coordinates leave the machine. The Map view is `React.lazy`-loaded (Leaflet + a 750 KB outline chunk); Leaflet is not testable in jsdom, so `MapExplorerView.test.tsx` mocks `LeafletMap` and the logic lives in `utils/geo.ts` and `maps/markers.ts`. HEIC/HEIF (pillow-heif) and camera RAW (rawpy: embedded preview) decode through `infrastructure/image_decoding.py`, shared by the extractor and the thumbnailer. A photo without an EXIF date has `captured_at = None` (sorted last); `sync --reextract` repairs records from before that rule.

If `frontend/dist/` exists, FastAPI serves it at `/` (assets mounted at `/assets`). Otherwise `/` returns a 404 page saying the frontend is not built. The frontend uses relative `/api` URLs everywhere (`frontend/src/api/client.ts`), which is why both the Vite proxy and the same-origin FastAPI serving work. State lives in Zustand stores (`stores/`). The server filters, sorts and pages the library: `usePhotoSearch()` (`hooks/usePhotos.ts`) is one `useInfiniteQuery` per filter set against `POST /api/search` (200 a page; key `['photos', 'search', request]`), built from the store's filters by `utils/search.ts`. All photo queries share the `['photos']` prefix (the map's geotagged set, single records); counts and analytics come from `GET /api/facets` (`useFacets`, key `['facets']`), and Select All uses `POST /api/search/ids`. Edits go through `hooks/usePhotoMutations.ts` (`useCuration`): optimistic update of every cached copy, replaced by the server record on success, rolled back per photo on failure, with an error toast; facets are refetched after. **URL state** (ticket 14): view, filters, sort, search by meaning and `inspectedHash` live in `stores/useViewStore.ts`, mirrored to the URL by `startUrlSync()` (`utils/urlState.ts`; `q` is the query bar's language; pushState for filters, replaceState for the photo); `useUiStore` holds only transient UI state, and `test/setup.ts` resets the view store before each test. `useInspectedPhoto()` serves the record from the cache or fetches it by hash, and reports `missing` for a stale `photo=` link. The desktop shell reopens the last query string (`<userData>/last-view.json`). `?demo=1` runs the same filter rules over sample data (`demo/demoLibrary.ts`). `App.tsx` shows distinct loading, error (with Retry) and empty-library states; sample data appears only with `?demo=1`. `api/client.ts` throws `ApiError` carrying FastAPI's `detail`. The UI follows `design_docs/front_enddesign.md` (nav rail, query bar, justified grid or table, chapter Timeline). The Library view (`gallery/LibraryView.tsx`) shows the justified grid (`PhotoGallery.tsx`, rows from the pure `utils/justifiedLayout.ts`, exact heights so nothing is measured) or the table (`PhotoTable.tsx`, fixed 38 px rows), both TanStack-virtualized; the Timeline (chapters from `utils/chapters.ts`) and Kanban views load further pages from a `LoadMore` footer. The query bar (`header/QueryBar.tsx`) edits the same store filters as the Library panel through the pure `utils/query.ts` (parse, resolve, tokens to filters and back; every `SearchRequest` filter has a token, including `near:`, `within:` and `ai:`, and `utils/queryRoundtrip.test.ts` fails when the OpenAPI document gains a field with no token: add the token, or list the field as not a filter there). Thumbnails are rendered upright by the backend (EXIF transpose) while stored `dimensions` are not, so aspect ratios swap for orientations 5-8 (`utils/photoFormat.photoAspectRatio`). Components read the Zustand stores through selectors (`useShallow`), and `PhotoCard` is memoised and reads `selectedHashes.has(hash)` directly, so do not rely on the non-reactive `isSelected()` helper for rendering.

### Desktop (Electron)

`desktop/src/main.ts` finds a free port (or reuses a healthy backend found via `/health`) and spawns the Python backend, either `scripts/desktop_backend.py` in dev or the PyInstaller bundle from `desktop/backend_dist` (copied to `resources/backend`) when packaged. It waits for the `DESKTOP_BACKEND_READY:<port>` line on stdout, then loads `http://127.0.0.1:<port>/`. When packaged it generates a per-launch token, passes it as `PMO_API_TOKEN` in the child's environment (never argv) and sets it as an HttpOnly, SameSite=Strict `pmo_token` cookie before loading the page; dev mode has no token. The backend keeps its data in the same OS per-user folders as the CLI (`api/desktop.py`: no path flags, log file always on). Packaged, the shell passes `--legacy-dir <userData>` and `--legacy-dir <resources>`: older builds kept `photos.db`, `thumbnails/`, `logs/` and `.cache/models` in `userData`; on first start the database is copied (never moved) and the model folder moved, once, by `adopt_legacy_data`. `desktop/dist-electron/*.js` is tracked: rebuild it (`npm --prefix desktop run build:electron`) after editing `desktop/src`. Do not set `win.signAndEditExecutable: false` in `electron-builder.json`: the exe then keeps Electron's identity and antivirus flags it. The winCodeSign symlink error is fixed by Developer Mode or one elevated build. `preload.ts` exposes `window.electronAPI` (typed in `frontend/src/types/electron.d.ts`) for the native folder picker and backend info. `desktop:package` runs the frontend build first, but you must run `backend:package` yourself before packaging.

## Repo conventions

- `GLOSSARY.md` (repo root) defines the domain terms (Asset, File, Photo, Curation, Scan, ...). Use them in code, tests and docs. ADR-003 (accepted 2026-10-20) is the plan for the asset/file split and the platform changes; it is not implemented yet.

- `.github/instructions/` holds the project's rules. The ones that matter: Conventional Commits (`feat(scope): subject`), TDD (write or adjust tests first), type hints on all signatures, and 100-column lines for black and ruff. Run `python -m pytest` before committing, and keep coverage from dropping (README claims ~93%).
- Docs live in `DOCS/ARCHITECTURE.md` and `design_docs/PHASE_*.md`. `c4_docs.html`, `photo_meta_organizer_architecture.*`, `graph.json` and `scripts/*mermaid*` are generated architecture artifacts, not source.
